# 1.3.0 预览与四方向验证记录

验证日期：2026-11-15（北京时间）。测试使用真实 RK3566 NPU、USB 摄像头、Windows 原视频、XIAO ESP32-S3 Sense 相机及三星 Android 手机。私人视频、目标人物图片、密钥和 Wi-Fi 配置不随本记录发布。

## RK3566 四方向

两段用户原视频各抽取12帧，将每帧在内存中旋转为四个安装方向，使用板上 INT8 RKNN 模型推理。每段48组，共96组手动反向校正后 RGB 与正向输入逐字节相同，检测人数一致。两段视频四个方向的自动模式最终均选到正确校正角度；部分方向的初始1–2次样本尚在学习。

另将实际相机中的近距离半身画面作为回归输入，同样检查48组。手动48/48恢复，四个方向自动最终均恢复。命令同时断言手动恢复、检测人数和自动最终方向，分别输出 `four_direction_manual_npu=PASS` 与 `four_direction_auto_npu=PASS`。

```sh
poseguard-rk3566 --orientation-smoke MODEL.rknn VIDEO.mp4
```

这是实际板端 NPU 对旋转输入的验证，未声称完成摄像头外壳四个方向逐次拆装。自动判断仍依赖可见人体；不能从空画面保证识别安装角度。

实时复核曾发现旧自动逻辑将近距离半身误选为270°并一直锁住。修复增加头肩向量、眼睛/肩部方向证据及锁定后的周期复核。实时画面确认180°校正时头部与肩部恢复对齐，随后恢复自动模式。MIPI和网页使用同一校正图像；低于0.45置信度的骨架点不绘制。

## 真实预览链路

| 来源 | 实际链路和观测 |
| --- | --- |
| RK3566 USB 相机 | 板端→域名WSS→接收端；640×480 H.264，12帧采样约406 kbps、首帧约2.12秒；另一次 JPEG 采样约944 kbps。不同时间画面，不能将两数直接作为压缩倍率 |
| Android 显示 RK3566 | 已安装同签名1.3.0 APK，真实 H.264 持续显示超过一分钟；检测约23 FPS，手机实际预览约2–4.5 FPS；原始/姿态切换和右上状态正常 |
| App 下发方向 | 从 App 选择手动90°，板端收到版本3并实际转为90°，分辨率480×640；随后从 App 切回自动，板端确认版本4 |
| Windows 原视频 | 原视频推理程序→域名WSS→接收端，360×640 JPEG，收到12帧，采样约230 kbps、首帧约1.52秒，源检测约34 FPS |
| XIAO Sense | 已烧录并校验最终相机固件，保留原设备绑定与网络配置；均衡320×240 JPEG收到12帧，用时约6.07秒、首帧约2.03秒、采样约70 kbps；另验证640×480相机画面能在手机显示 |

手机验收发现 H.264 在有界流控中等显示确认会提前停止。改为确认进入有界解码队列，同时限制解码排队和元数据长度，实机持续观看通过。JPEG仍在解码后确认。暂停、关闭和切后台后停止观看，板端预览状态回到 inactive；本地检测继续。

Android 实际截图覆盖预览入口、清洁画面、骨架、FPS、方向设置、四个手动选项和应用回执。内置 Browser 服务加载失败，视觉验收使用真实手机 WebView 截图及已获允许的内置视觉检查；独立桌面浏览器和 iPhone 真机未验收。
