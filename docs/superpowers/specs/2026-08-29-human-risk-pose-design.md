# 金盾护农人体风险姿态预警系统设计规格

## 1. 目标与范围

第一阶段交付一个可在 Windows 摄像头或视频文件上运行的实时人体姿态跟踪原型。系统持续跟踪画面中的所有人员，为每个目标分配稳定 ID，并只对以下三类行为产生风险告警：

1. 监控区域内多人同时出现或彼此过近；
2. 单手持手机贴近耳部并保持站立姿态；
3. 同一人员在监控区域内停留时间超过阈值。

普通行走、单人短暂停留、抬手但没有手机、远处背景人员均保持正常状态。界面中正常目标使用黄色边框，候选状态使用橙黄色边框，确认风险使用红色边框，并显示目标 ID、风险原因和持续时间。

本阶段不实现云端上传、人脸识别、身份判断、声音识别或自动执法动作。视频默认只在本机处理，事件日志只保存去身份化的目标 ID、时间、风险类型和几何信息。

## 2. 产品约束

- 先完成 Windows 原型和本机摄像头验证，再讨论嵌入式部署。
- 代码结构、变量命名、时序判定、轨迹管理、风险融合和界面均采用独立设计，不复制参考项目的文件组织或控制流程。
- 不以规避 AI 识别为目标；对第三方模型、运行库和数据集保留清晰的来源与许可证说明。Ultralytics/YOLO 后端与业务判定层隔离，便于后续更换为具备合适商业授权的模型或运行时。
- 处理帧率优先保证连续性和低延迟。默认将摄像头帧缩放到不超过 960 像素宽后推理，显示帧保留原比例。
- 所有风险阈值放入配置文件，不把阈值散落在推理代码中。

## 3. 方案选择

### 方案 A：YOLO11n-pose + 条件式手机检测 + 原创时序规则引擎（采用）

姿态模型持续输出人体框和关键点；仅当某人的手腕进入耳部候选区域时，才触发手机目标检测。轨迹管理器为人员建立稳定 ID，风险引擎用连续帧、时间窗口和滞回状态确认行为。该方案适合快速形成 Windows 原型，同时能把误报控制在“手腕靠近耳朵但没有手机”的场景之外。

### 方案 B：仅 YOLO11n-pose 的手腕-耳部几何规则

实现最快、计算量最低，但无法可靠区分打电话、挠头和整理头发，只适合早期联调，不作为正式判定方案。

### 方案 C：端到端动作分类模型

直接对多帧姿态序列训练行为分类器，长期定制空间更大，但需要采集和标注大量真实场景数据，不能满足当前快速进入测试阶段的要求。

第一阶段使用方案 A，并让手机检测成为可关闭的后端能力：当手机模型不可用时，系统仍能运行，但贴耳行为只显示候选黄色状态，不升级为确认红色。

## 4. 系统架构

```text
摄像头/视频文件
        |
        v
帧采集与尺寸控制
        |
        v
PoseBackend(YOLO11n-pose)
        |
        +--> PersonTrackManager —— 稳定ID、短时丢失保持、轨迹平滑
        |             |
        |             +--> PhoneBackend(候选目标才调用)
        |             |
        |             v
        |       RiskRuleEngine
        |             |
        |             v
        +--> OverlayRenderer —— 黄/橙/红框、原因、计时、FPS
                      |
                      v
              EventLog(JSONL，可选截图)
```

计划的项目边界如下：

- `poseguard/app.py`：命令行入口、摄像头/视频循环和退出处理。
- `poseguard/config.py`：配置加载、默认值和参数校验。
- `poseguard/backends/pose_backend.py`：姿态推理的抽象接口。
- `poseguard/backends/yolo_pose_backend.py`：Windows 的 YOLO11n-pose 适配。
- `poseguard/backends/phone_backend.py`：手机目标检测接口和可选实现。
- `poseguard/tracking/person_tracks.py`：原创的轻量轨迹匹配和状态平滑。
- `poseguard/risk/risk_engine.py`：多人、疑似与他人通话、长时间停留状态机。
- `poseguard/risk/geometry.py`：关键点距离、相对尺度、区域和邻近关系计算。
- `poseguard/ui/overlay.py`：绘制边框、标签、风险原因和统计信息。
- `poseguard/io/event_log.py`：去身份化事件记录。
- `poseguard/tests/`：规则、轨迹、配置和离线帧序列测试。
- `poseguard/configs/windows.json`：Windows 默认配置。

每个推理后端只负责输出统一的检测数据，不参与风险决策；风险引擎不依赖 PyTorch、OpenCV 或具体模型库。这样后续替换 RKNN、MaixCAM 或其他推理接口时，业务逻辑和测试可以复用。

## 5. 检测与跟踪规则

### 5.1 人体跟踪

每帧姿态检测结果转换为统一的人体记录：`track_id`、框、置信度、17个关键点、关键点置信度、中心点和时间戳。轨迹匹配综合框中心距离、框面积变化和可用关键点距离；短暂漏检时保留轨迹若干帧，超过失联时间才删除。轨迹坐标使用指数平滑，避免检测框轻微抖动造成告警闪烁。

### 5.2 疑似与他人通话

候选条件同时满足：

- 至少一侧腕点和同侧耳点有效；
- 腕点到耳点的距离小于人体框高度的比例阈值；
- 同侧肘、腕、肩形成合理的抬臂几何关系；
- 人体处于近似站立状态，排除明显躺坐姿；
- 可选手机检测框位于耳部-手腕连线附近或与手部区域相交。

候选状态先显示橙黄色。手机实物匹配成功，或在配置的连续确认窗口内姿态稳定成立，才升级为红色“疑似与他人通话”。连续若干帧不满足条件后降级，采用独立的触发/解除阈值避免红黄快速跳变。

### 5.3 多人风险

只统计监控区域内的稳定轨迹，不把画面边缘或远处背景目标直接视为风险。默认两名以上目标同时进入区域并保持约 1.5 秒触发“多人聚集”；若目标之间距离低于人体框尺度归一化阈值，显示“多人过近”。参数可分别配置。

### 5.4 长时间停留

目标首次稳定进入监控区域时记录开始时间。只要目标仍在区域内且轨迹有效，累计停留时间；默认超过 20 秒触发“长时间停留”。离开区域或连续丢失超过释放窗口后清除计时。停留判断使用轨迹中心的移动距离和区域占比，而不是依赖某个固定像素坐标。

### 5.5 风险融合

每个目标拥有 `normal`、`candidate`、`alert` 三态；系统级还维护多人聚集事件。相同目标的多个风险原因合并显示，但事件日志分别记录原因。触发与解除均采用时间窗口，避免单帧误检直接变红。

## 6. Windows 试运行体验

默认命令运行本机摄像头，参数可切换视频文件、模型路径、显示开关和配置文件。窗口显示：

- 所有人的稳定 ID和姿态骨架；
- 黄色正常框、橙黄色候选框、红色风险框；
- 风险原因和持续时间；
- 当前 FPS、推理耗时、跟踪人数；
- 最近事件摘要。

提供 `q`/ESC 退出和 `p` 暂停显示，视频失效、模型缺失或手机后端不可用时给出可读错误并安全释放摄像头。事件以 JSONL 写入 `runs/`，不默认保存原始视频。

## 7. 测试策略

在接入真实摄像头前，先用不依赖模型的合成轨迹和关键点数据测试：

- 单人正常活动不告警；
- 两人达到区域和时间条件后告警；
- 腕点靠耳但没有手机只保持候选；
- 手机匹配并连续稳定后升级红色；
- 目标短暂漏检不会立刻换 ID或清空停留时间；
- 离开区域后停留事件按释放窗口结束；
- 配置阈值、无效输入和后端异常有明确结果。

随后使用 Windows 摄像头做人工回放测试，记录 FPS、端到端延迟、漏检恢复时间和三类风险的误报/漏报样本。性能数据只作为当前机器基线，不把 PPT 中的指标直接当成已验证结果。

## 8. 嵌入式迁移边界

三个目标设备都是可以脱离其他计算设备独立工作的端侧终端。每台设备都在本机完成摄像头采集、人体检测或姿态估计、多人轨迹维护、风险状态判断和本地/联网告警；设备之间不互相依赖，也不采用“一个设备采集、另一个设备推理”的固定分工。

- 泰山派 RK3566：连接 USB 摄像头，优先将轻量姿态模型转换为 RKNN INT8，在板载 NPU 上完成主推理。轨迹、风险规则和告警均在板端运行；手机检测可在贴耳候选出现后按间隔触发，以控制负载。
- MaixCAM Pro：使用板载摄像头和 MaixPy/MaixCDK 可用的 NPU 推理链，独立运行轻量姿态模型、轨迹管理、风险规则和告警。YOLO11 姿态头能否直接转换必须通过实机算子和输出验证；不兼容时更换姿态网络结构，但保持统一数据语义。
- XIAO ESP32-S3 Sense：使用板载 OV3660 摄像头，独立完成低分辨率采集、轻量人体姿态/关键点推理、简化轨迹、三类风险判断和告警。它不直接照搬完整 YOLO11n-pose，而采用为 8MB PSRAM/8MB Flash 约束单独蒸馏、剪枝和 INT8 量化的 TinyML 模型；必要时将手机实物确认改为轻量局部分类器，但仍由设备本机完成，不依赖 RK3566 或 MaixCAM。
- 三个平台共享风险类型、状态颜色、事件字段和配置语义。可共享的纯规则逻辑优先复用；受语言、内存和运行时限制时允许等价重写，并通过同一组合成测试向量验证行为一致性。
- 平台差异集中在摄像头驱动、图像尺寸、模型结构、推理后端、缓存规模和告警输出适配层，不改变“单设备端侧闭环”的产品要求。

## 9. 交付与版权说明

Windows 第一阶段交付包含源码、配置、运行说明、测试报告模板和依赖许可证清单。原创部分重点体现在：统一数据协议、轨迹匹配、几何特征组合、时序状态机、风险融合、去身份化事件格式和可迁移后端结构。第三方模型权重、推理库、OpenCV和其他组件单独列明来源与许可证，不将第三方代码伪装为原创。

在决定闭源商业发布前，必须根据最终采用的模型权重、Ultralytics运行库和部署方式完成许可证复核；若授权条件不适合，将替换后端而不改动风险引擎和测试体系。

## 10. 第一阶段完成标准

以下条件全部满足才进入嵌入式优化讨论：

1. Windows 摄像头能持续运行并显示多人稳定 ID；
2. 三类风险均能按时间窗口触发和解除；
3. 贴耳姿态没有手机实物时不会直接变成确认红色；
4. 摄像头短时漏检不会造成目标 ID和计时剧烈跳变；
5. 离线规则测试通过，应用能安全退出并释放摄像头；
6. 运行说明和许可证清单完整；
7. 真实测试数据记录当前机器的 FPS、延迟和典型误报样本。
