# PoseGuard MaixCAM Pro 端侧版本设计

## 目标

在 MaixCAM Pro 上形成完全本机运行的最小可用闭环：

```text
板载摄像头 -> YOLO11n-Pose 320x224 INT8 -> 17 点姿态
           -> 多人轨迹 -> 风险状态机 -> 屏幕叠加与事件告警
```

第一版优先保证链路短、响应稳定和便于现场调参，不依赖 Windows、RK3566 或网络推理服务。

## 已确认的技术选择

- 运行环境采用板上现有 MaixPy 4.12.5。
- 姿态推理直接使用 `/root/models/yolo11n_pose.mud`，其底层模型输入为 320×224 INT8。
- 摄像头使用 MaixCAM Pro 板载 MIPI 摄像头；采集尺寸与模型输入一致。
- 单帧只运行一次姿态模型。第一版不增加常驻的第二个检测模型。
- 风险行为限定为：多人进入监控区、疑似单手贴耳站立、疑似长时间停留。
- 黄色表示正常跟踪，橙色表示候选风险，红色表示确认告警。
- 初次部署目录为 `/root/poseguard_maix/`，手动启动验证，不覆盖板上现有 `/root/main.py`。

## 工程结构

本地新增 `platforms/maixcam/`，各文件只承担一个职责：

```text
platforms/maixcam/
├── main.py             # 初始化资源并驱动逐帧闭环
├── config.py           # 模型、阈值、ROI、计时与路径配置
├── pose_adapter.py     # MaixPy 检测结果转为统一 17 点观测
├── track_core.py       # 轻量多人关联、平滑和短时丢失保持
├── risk_core.py        # 三类风险的时间状态机与融合
├── screen.py           # 屏幕骨架、框、标签和性能信息
├── event_store.py      # 告警状态变化的 JSONL 记录
└── deploy.ps1          # 从 Windows 复制文件并执行板端自检
```

MaixCAM 端不直接导入 Windows 版本的 OpenCV、Ultralytics、Pillow 或 dataclass 实现。它复用相同的字段含义和风险语义，但以 MaixPy 可运行的轻量 Python 代码实现。

## 主循环与数据流

`main.py` 按以下固定顺序处理每帧：

1. 从板载摄像头取得当前帧；不建立待处理帧队列。
2. 调用 MaixPy `nn.YOLO11` 姿态推理。
3. `pose_adapter.py` 检查人体框和 17 点完整性，过滤过低置信度、过小框和明显越界结果。
4. `track_core.py` 将观测关联到稳定递增 ID，并对框和关键点做指数平滑。
5. `risk_core.py` 更新每条轨迹的候选、确认和解除计时器。
6. `screen.py` 在当前帧上绘制骨架、ID、风险标签、FPS 和推理耗时，然后送往板载屏幕。
7. 仅在风险状态发生变化时由 `event_store.py` 追加事件。

推理启用 `dual_buff=True` 时允许模型流水线产生一帧结果延迟；轨迹和风险判断始终使用该结果对应的单调时间戳，避免计时器受显示刷新影响。

## 姿态适配

适配层输出以下最小记录：人体框、人体置信度、17 个 COCO 点、检测序号。MaixPy 返回 34 个按 `x, y` 交错排列的整数；坐标为 `-1` 的遮挡点转换为空值，其余点保留为模型输入图像坐标。逐点筛选由 `detect(..., keypoint_th=0.5)` 完成，不虚构模型没有返回的逐点置信度。

过滤条件包括：

- 人体置信度低于配置阈值；
- 可用关键点少于 6 个，或肩/髋等躯干点少于 3 个；
- 人体框面积小于画面的 1.5% 或大于 80%；
- 人体框位于画面外的面积超过框面积的 20%；
- 两个结果的 IoU 大于 0.45，且中心距离小于较小人体高度的 0.25 时，只保留人体置信度较高者。

## 多人轨迹

板端场景最多保留 6 条轨迹，使用固定上限避免历史数据持续增长。关联代价由人体中心距离、框面积变化和共有关键点距离组成，全部按人体高度归一化。

- 新轨迹连续命中 2 帧后才对外显示。
- 框和关键点采用指数平滑，默认新观测权重为 0.55。
- 短时漏检时保留最近状态最多 0.8 秒，但预测轨迹不新增风险证据。
- 超过保持时间后删除轨迹；ID 不循环复用。
- 每条轨迹只保存当前状态、上一帧状态、累计路径和风险计时器，不保存完整姿态历史。

## 风险规则

### 多人进入监控区

监控 ROI 内同时存在至少 2 条已确认、当前可见轨迹时进入候选；持续 1.2 秒后转为红色告警。任一人员离开或丢失后，保留红色 0.8 秒再解除，防止边界抖动。

### 疑似单手贴耳站立

该规则判断“疑似贴耳姿态”，不把姿态结果描述为手机实物检测。候选需同时满足：

- 左腕接近左耳或右腕接近右耳，距离小于人体高度的 0.14；
- 只有一侧满足贴耳条件，减少双手抱头、瑜伽动作等误报；
- 对应肘点、肩点可见，腕—耳距离小于肘—耳距离，且肘—腕长度不小于人体高度的 0.08；
- 双肩和双髋可计算中点，肩髋主轴满足 `abs(dx) / max(abs(dy), 1) <= 0.45`；
- 至少一侧髋和膝可见，膝位于髋下方且肩中点到膝的垂直跨度不小于人体高度的 0.42；若同侧踝可见，还必须位于膝下方。

满足几何条件时显示橙色；同一侧连续保持 1.0 秒后变为红色。左右侧切换、关键点不足或姿态不再满足时重置候选计时；已确认告警延迟 0.8 秒解除。

### 疑似长时间停留

轨迹中心位于 ROI 内，累计 20 秒、平均移动速度不高于每秒 0.12 个当前人体高度，且关键点姿态运动量不高于每帧 0.04 个当前人体高度时触发红色告警。任一运动阈值连续 2 帧超限即重置停留计时，避免把原地运动误判为静止逗留。

### 风险融合

同一轨迹可同时满足多种规则。显示颜色取最高状态，标签合并去重后的风险原因；事件则按风险类型分别维护触发和解除状态。

## 屏幕与事件

板载屏幕每帧显示：

- 人体框、17 点骨架和稳定 ID；
- 正常、候选或告警颜色；
- 当前风险短标签及持续时间；
- 当前人数、FPS、模型推理毫秒数。

事件写入 `/root/poseguard_maix/data/events.jsonl`。每条记录包含时间、轨迹 ID、风险类型、状态、持续时间、当前人数和性能指标。只记录状态变化，写入失败时打印一次节流错误并继续视觉主循环。

## 异常处理

- 模型加载失败：输出明确路径与异常并退出，不继续打开摄像头。
- 摄像头取帧失败：关闭摄像头，按 0.5、1、2 秒退避重开；成功后清空轨迹和风险计时器。
- 屏幕初始化失败：进入无屏模式，继续推理并记录事件。
- 单个检测结果格式异常：丢弃该目标，不终止整帧。
- 单帧推理异常：记录节流日志并继续下一帧；连续失败 5 帧后重新初始化模型。
- 退出或键盘中断：按显示、摄像头、模型的逆序释放资源。

## 部署方式

`deploy.ps1` 通过 SSH/SCP 将 `platforms/maixcam/` 同步到 `/root/poseguard_maix/`，然后依次执行：

1. 导入检查；
2. 模型加载与输入尺寸检查；
3. 无屏处理若干帧的冒烟测试；
4. 用户确认后启动有屏主程序。

首轮联调使用手动命令启动。连续运行验证通过后，再单独决定是否接入板端开机启动配置。

## 测试与验收

纯逻辑模块先在 Windows 上使用合成 17 点输入验证：

- 单人正常、多人候选与确认；
- 单手贴耳站立触发，双手抱头和瑜伽动作不触发；
- 长时间静止触发，走动或明显姿态运动重置；
- 短时漏检不换 ID，预测帧不积累风险证据；
- 告警状态变化只产生一次事件。

板端首轮验收条件：

- 连续处理 300 帧无未捕获异常；
- 屏幕同步显示人体框、17 点和稳定 ID；
- 三类风险可通过缩短测试计时现场触发并正确解除；
- 320×224 链路实测不产生帧队列累积，平均速度不低于 10 FPS；
- 恢复正式计时配置后连续运行 5 分钟，事件文件可读且状态无持续乱跳。

## 第一版不做的内容

- 不训练或转换新的姿态模型；
- 不运行人脸识别、身份判断或诈骗结论分类；
- 不保存原始图片或视频；
- 不加入云端推理、网页后台和远程控制；
- 不改动 Windows、RK3566 和 ESP32-S3 版本；
- 不覆盖板上现有 `/root/main.py`，也不在首轮验证前配置开机自启。
